/dev

Magnitude-Aware SDLC Pipeline — From idea to ship-ready code in one command

How to Use

> /dev
> /dev add user authentication with OAuth2
> /dev fix the null pointer in the payment handler
> /dev update the README with new API docs

Type /dev optionally followed by a task description. The command classifies the task's magnitude and runs proportional ceremony — a typo fix skips councils and audits, a new module gets the full pipeline with parallel agents and adversarial code review.

Architecture

Hybrid design: SKILL.md handles interactive phases (needs user input), Workflow JS handles parallelizable phases (runs in background with deterministic loops).

SKILL.md Interactive

  • Phase 0: Triage + cost estimate
  • Phase 1: Brainstorm (asks questions)
  • Phase 2: Design Council (user reviews verdict)
  • Phase 3: Write plan
  • Phase 4: Set up worktree
  • Phase 9: Ship Council (user reviews verdict)
  • Phase 10: Docs check
  • Phase 10.5: Knowledge Quiz (interactive)
  • Phase 11: Finish (merge/PR/commit)

implement-and-review.js Parallel

  • Phase 5: Parallel implementation (1 agent per task)
  • Phase 5b: Integration agent (merge worktrees)
  • Phase 6: Verify + debug loop (max 3 cycles)
  • Phase 7: Code review + adversarial verify
  • Phase 7b: Graduated remediation (max 3 cycles)
  • Phase 8: Parallel audits + remediation

Magnitude Triage

Phase 0 classifies every task into one of three levels. This is the single source of truth — all phase skip/run decisions derive from it.

TRIVIAL Config, typo, 1-file fix, deps, style-only

Triage → Implement → Verify → Security* → Docs → Quiz → Finish

TDD optional. No councils. No worktree. Security* if HAS_FRONTEND/HAS_API. 5-question quiz. ~20K tokens.

STANDARD Feature, multi-file, bug fix, API change

Triage → Brainstorm → Plan → Worktree → Workflow (5-8) → Ship Council → Docs → Quiz → Finish

TDD mandatory. Ship council only. Worktree isolated. Conditional audits. 10-question quiz. ~120K tokens.

COMPLEX Architecture, new module, cross-cutting, security

Triage → Brainstorm → Design Council → Plan → Worktree → Workflow (5-8) → Ship Council → Docs → Quiz → Finish

TDD mandatory. Both councils. Worktree isolated. Conditional audits. 12-question quiz. ~250K+ tokens.

Dynamic re-evaluation: Triage is not final. Magnitude is re-evaluated at 2 checkpoints (after codebase analysis, after first implementation). Upward reclassification by default; downward with user confirmation only. Dirty-tree handling via git stash on escalation.

Phase-by-Phase Breakdown

Phase 0: Triage + Cost Estimate T S C

Step 0a — Resume check (always first). Resolve the project root, look for HANDOFF.md and .dev-pipeline-state.json, and read the handoff in full before anything else. Reconciles what was found against the user's current request: resume / treat as prior context / archive and start fresh. See Handoff File.

Exit invariant: HANDOFF.md exists at the project root before Phase 0 ends — on every path. A state file with no handoff (pipeline started by an older version of the skill, or handoff deleted) is backfilled from the state file plus git, not skipped and not handed back to the user to reconstruct.

Step 0b — Fresh pipeline:

  1. Get task description (from /dev <args> or ask user)
  2. Classify magnitude: TRIVIAL / STANDARD / COMPLEX
  3. Show classification + active phases + advisory cost estimate
  4. Ask user: proceed / override / abort
  5. Create task list, write initial .dev-pipeline-state.json
  6. Resolve project root, write initial HANDOFF.md there

Cost estimates are advisory — Claude Code has no runtime token counter.

Phase 1: Brainstorm S C

Skill: superpowers:brainstorming

Explores project context, asks clarifying questions one at a time, proposes 2-3 approaches with trade-offs, presents design for user approval. Saves design doc to docs/superpowers/specs/.

Phase 2: Design Council C

Skill: llm-council (5 advisors + peer review + chairman)

Councils the design for implementation-readiness: soundness, completeness, scope, risk. GO → proceed. NO-GO → Council Remediation Loop (max 5 iterations).

Phase 3: Write Plan S C

Skill: superpowers:writing-plans

Maps file structure, defines bite-sized tasks with TDD steps. Saves to docs/superpowers/plans/.

Phase 4: Git Worktree S C

Skill: superpowers:using-git-worktrees

Creates isolated workspace on a feature branch. All implementation happens in the worktree.

Phases 5-8: Implement + Verify + Review + Audit WORKFLOW

For STANDARD/COMPLEX, these 4 phases run as a single background Workflow with parallel agents and deterministic JS loops. For TRIVIAL, runs inline without the workflow. Security audit runs for ALL magnitudes when changed files match HAS_FRONTEND or HAS_API.

5. Implement (parallel)

One agent per task, each in its own isolated worktree. All tasks run in parallel. Integration agent merges results and resolves conflicts.

6. Verify (loop: max 3 cycles)

Full test suite. On failure: systematic debugging → fix → re-test. Repeats up to 3 times. Falls back to build verification if no test script exists.

7. Code Review (adversarial)

Maestro structured review → conditional 2nd review (only if HIGH+ found) → adversarial verify (independent agents try to refute each HIGH+ finding) → graduated remediation loop (max 3 cycles).

8. Conditional Audits (parallel)

Auto-triggered by changed file types. Security, accessibility, performance audits run in parallel. Remediation loop (max 3 cycles) for HIGH+ findings.

Phase 9: Ship Council S C

Skill: llm-council

Councils the implementation for ship-readiness. Includes: summary, test results, review findings, audit results, diff stats. GO → proceed. NO-GO → re-runs the Workflow with council feedback (max 5 iterations).

Phase 10: Documentation Check T S C

Scans changed files. Checks: README, CLAUDE.md, API docs, inline docs, design doc (marks IMPLEMENTED), changelog. Updates stale docs.

Phase 10.5: Knowledge Quiz T S C

Interactive knowledge quiz on the newly completed implementation. Purpose: ensure the developer maintains full awareness and ownership of code authored by Claude.

  • TRIVIAL: 5 questions
  • STANDARD: 10 questions
  • COMPLEX: 10 questions + 2 architectural bonus questions

Mix: ~40% on what changed, ~30% on how it works, ~30% on why (design decisions). Evaluation per answer: ✅ correct, ⚠️ partial, ❌ incorrect with file:line reference.

Non-blocking — purely informative result, does not block Phase 11.

Phase 11: Finish T S C

STANDARD/COMPLEX: superpowers:finishing-a-development-branch — merge, PR, or cleanup.

TRIVIAL: Simple finish — commit, leave unstaged, or discard.

Agent Communication Patterns

Agents don't talk directly. The Workflow script mediates all communication by passing results between agents.

1. Chain

Output of each phase becomes input of the next. No context loss between stages.

Agent A (implement) → result → Agent B (verify) → result → Agent C (review)

2. Adversarial Verify

After review, each HIGH+ finding gets an independent verifier that tries to refute it. Only confirmed findings proceed to remediation. Eliminates false positives.

Reviewer finds 5 HIGH issues
  → 5 parallel verifiers try to refute each
  → 3 confirmed, 2 refuted
  → Only 3 go to remediation (saved 2 unnecessary fix cycles)

3. Panel (Council)

5 independent advisors with different thinking styles + anonymous peer review + chairman synthesis. Based on Karpathy's LLM Council methodology.

4. Integration Agent

After parallel implementation in isolated worktrees, a dedicated agent merges all results and resolves merge conflicts.

Remediation Loops

All loops have hard caps. Technical loops (verify, review, audit) use deterministic JS for loops. Council loops use prompt-level iteration with user interaction.

Verify → Debug Loop (Workflow JS)

for (attempt = 0; attempt < 3; attempt++) {
  run tests → if pass: break
  systematic debug → fix root cause → loop
}
// After 3 failures: return FAILED

Graduated Remediation Loop (Workflow JS)

for (cycle = 0; cycle < 3; cycle++) {
  LOW/MEDIUM → fix inline, re-verify only
  HIGH → fix, re-verify, lightweight re-review
  CRITICAL → amend plan, re-implement, full verify + review
}
// After 3 cycles: remaining findings reported to council

Council Remediation Loop (SKILL.md)

while (council says NO && iterations < 5) {
  extract feedback → remediate → re-council
}
// After 5: ask user — continue / force-proceed / abort / reset

State Persistence & Rollback

Pipeline State

Written to .dev-pipeline-state.json after every phase completion, reclassification, and remediation cycle.

Fields: task, magnitude, currentPhase, completedPhases, rollbackSHA, remediationCounts, designDoc, planDoc, worktreePath, startedAt.

Resume: Phase 0 Step 0a. If found: "Found interrupted pipeline — Resume / Restart / Abort?"

Cleanup: Deleted on pipeline completion or user abort.

Handoff File — HANDOFF.md

The state file is machine state (phases, gates, booleans). HANDOFF.md is why and where we are, in prose, written for a Claude with zero memory. It exists so a /clear, a compaction, or a new session the next morning does not cost you the context you paid for.

Location. Project root — not necessarily the directory Claude was launched from. Resolved once at Phase 0, first hit wins:

  1. worktreePath from Phase 4, if a worktree exists
  2. git rev-parse --show-toplevel from the directory of the files being changed
  3. Nearest ancestor holding package.json / pyproject.toml / go.mod / Cargo.toml / pom.xml / .git / CLAUDE.md
  4. cwd — and Claude says so out loud, because it may be wrong

Contents. Rewritten in full at every phase completion, every reclassification, every failure, and at context exhaustion:

SectionWhat it carries
GoalThe ask in the user's own terms + the acceptance condition
Where we areCurrent phase, completed vs remaining, gate status
Next stepThe next concrete action, specific enough to execute cold
Files touchedChanged files and files merely read — the slow-to-rebuild context
Key decisionsDecision + reason + the alternative that was rejected
Failures & dead endsWhat was tried, the verbatim error, how it resolved
Do NOTApproaches already ruled out — stops a fresh Claude re-treading them
Open questionsPending user decisions
Waived / deferredFindings consciously not fixed, and who waived them
CommandsTest / build / lint / run — only ones actually verified this session

Lifecycle. Created at Phase 0, refreshed after every phase, and kept at Phase 11 with Status: DONE — unlike the state file, it is not deleted. It is the record of what was built and what was deliberately left undone.

Self-healing. The file is created whenever it is found missing, never merely expected to be there. Phase 0 guarantees one on every path; each subsequent phase entry re-checks and writes one if absent. A pipeline that predates this feature, or whose handoff was deleted, is backfilled from .dev-pipeline-state.json plus git status / git diff --stat <rollbackSHA>, with the sections that cannot be recovered (dead ends, decisions, verified commands) marked (not recorded — predates handoff tracking). Partial beats absent.

Stale pipelines. When the recorded task does not match what you are asking for now, /dev does not resume it. It reports what the old pipeline was, archives it to HANDOFF.prev.md, and offers: resume the old task, archive it and start the new one, or abort.

Rules. Facts only, no plans described as done. Errors quoted verbatim. Under ~150 lines. Never any secrets — it is plaintext in the repo.

Session Isolation & Collisions

The SessionStart hook ~/.claude/hooks/dev-handoff-detect.js surfaces any interrupted handoff at session start, so /dev finds it even when Claude has no memory of writing it.

The hook is a per-session child process: it reads that session's cwd from stdin and its output reaches only that session's context. Multiple terminals never cross-talk. It exits silently when there is nothing to report, so it costs nothing in unrelated sessions.

ScenarioOutcome
Several terminals, different reposIsolated by cwd — nothing to do
Same repo, different worktreesIsolated — each worktree is its own root
Same repo, same directoryReal collision — handled below

For the last case, HANDOFF.md stamps Session: <id> (pid <n>). Before its first write, /dev checks whether a different owning pid is still alive. Alive means a second terminal is genuinely running a pipeline here: Claude stops and offers a separate worktree, a takeover, or an abort. A dead pid is just your own earlier session — taken over silently, no warning. No lock files, so nothing to clean up after a crash.

Rollback

  • Worktree delete — discards all changes instantly
  • SHA reset — captured before implementation, stored in state file. git reset --hard <rollbackSHA>
  • User abort — always available, state preserved for later resume

Pros & Cons

Pros

  • Proportional ceremony — trivial tasks skip everything; complex tasks get full pipeline
  • Parallel execution — implementation, reviews, and audits run concurrently
  • Adversarial review — HIGH+ findings pressure-tested; false positives eliminated
  • Deterministic loops — JS for loops, not LLM-estimated counters
  • Schema validation — agent responses validated via JSON Schema
  • Resumable — state persisted to JSON; resume on session interruption
  • Rollback — SHA capture + worktree isolation = always recoverable
  • Dynamic triage — reclassifies if task is bigger than expected
  • 15+ specialized skills — each phase uses purpose-built tooling
  • Council quality gates — multi-perspective adversarial review before shipping

Cons

  • Token cost — COMPLEX runs can exceed 250K tokens with councils
  • Context window pressure — long pipelines may trigger compaction, losing earlier context
  • No user interaction during Workflow — if implementation needs clarification, agent returns BLOCKED
  • Worktree + monorepo friction — may need npm install in worktree
  • Council is same-model — 5 advisors are the same LLM with different prompts, not different models
  • Token estimates are advisory — no runtime counter available
  • Requires test infrastructure — TDD phases need a working test framework
  • Two files to maintain — SKILL.md + workflow JS script

Design History

This command was iteratively designed through 4 LLM Council reviews, each finding issues and driving improvements.

v1 — Initial Design

11 phases, 2 mandatory councils, full pipeline always, TDD mandatory. Council found: over-engineered — no triage, no graduated remediation, overkill for solo dev.

v2 — Added Triage

Magnitude-aware triage (trivial/standard/complex), conditional phases, advisory cost estimates. Council found: triage is static (no re-evaluation), no loop counters, token budget unenforceable.

v3 — Added Persistence + Loops

Dynamic triage, pipeline state persistence, remediation loop counters, conditional dual review, rollback SHA in state file. Council found: remediation duplicated 3x, state file in wrong location, shell variable doesn't persist.

v4 — Stabilized + Compressed

Deduplicated remediation, fixed state persistence, honest about token counter limitation. Compressed from 666 to 151 lines. Council found: ready to test. "Stop reviewing, start using."

v5 — Hybrid Architecture

Switched Phases 5-8 from sequential Skills to parallel Workflow JS. Added adversarial verify, integration agent, deterministic loops. Empirically tested on TRIVIAL task.

v5.2 (current) — Handoff & Resume

Added HANDOFF.md: a human-readable context snapshot in the project root, written at Phase 0 and refreshed every phase, so a /clear or a new session does not lose the goal, the dead ends, or the next step. Phase 0 gained Step 0a, an unconditional resume check that runs before anything else, plus a SessionStart hook that surfaces the file automatically. Project root is now resolved explicitly rather than assumed to be the launch directory. Concurrent sessions in the same directory are detected via a live-pid check instead of lock files.
